# Day 7 Assignment: SnapShare Scaling Plan

## 1. Assumptions

SnapShare is a photo-sharing application where users upload photos and scroll through a feed containing photos from people they follow.

The following assumptions are used for these estimates:

- Registered users: 10,000,000.
- Daily active users: 10% of registered users.
- Each active user uploads 1 photo per day.
- Each active user views 50 feed pages per day.
- Average original photo size: 2 MB.
- Each photo also has one thumbnail of 50 KB.
- One day has 86,400 seconds.
- Peak traffic is estimated at 5 times the average traffic.
- Storage estimates use decimal units: 1 GB = 1,000 MB and 1 TB = 1,000 GB.
- Every uploaded photo is retained for a full year. The estimates exclude database overhead, backups, replication copies, and storage reductions from compression or deduplication.

### Daily active users

Daily active users (DAU) = Registered users × Active percentage

10,000,000 × 10% = **1,000,000 daily active users**

## 2. Traffic and Storage Estimates

### Uploads per second

Each daily active user uploads one photo per day.

Uploads per day = 1,000,000 × 1 = 1,000,000 uploads

Average uploads per second = 1,000,000 ÷ 86,400

**Average: approximately 11.6 uploads per second**

Peak uploads per second = 11.6 × 5

**Peak: approximately 58 uploads per second**

### Feed views per second

Each active user views 50 feed pages per day.

Feed views per day = 1,000,000 × 50 = 50,000,000 views

Average feed views per second = 50,000,000 ÷ 86,400

**Average: approximately 579 feed views per second**

Peak feed views per second = 579 × 5

**Peak: approximately 2,895 feed views per second**

### Photo storage per year

Original photo storage per day:

1,000,000 photos × 2 MB = 2,000,000 MB = 2 TB per day

Original photo storage per year:

2 TB × 365 = **730 TB per year**

Thumbnail storage per day:

1,000,000 thumbnails × 50 KB = 50,000,000 KB = 50 GB per day

Thumbnail storage per year:

50 GB × 365 = **18.25 TB per year**

Total estimated photo and thumbnail storage:

730 TB + 18.25 TB = **748.25 TB per year**

These figures represent the data generated by one year's uploads, before accounting for replication, backups, retention policies, or compression.

## 3. Read-Heavy or Write-Heavy?

SnapShare is a **read-heavy system** because users generate approximately 50 million feed views per day compared with 1 million photo uploads per day. That is about 50 feed views for every upload.

The architecture should therefore optimise photo and feed delivery. A cache can reduce repeated database queries, a CDN can serve photo files from locations closer to users, and a read replica can handle database read traffic. Uploads must still be stored reliably, so the design also needs durable object storage and background processing for thumbnails.

## 4. Why Photos Should Not Be Stored Inside the Database

Photos are large binary files, and storing them directly inside the main relational database would increase its size, backups, and storage costs. Large file reads could also compete with database operations needed for user accounts, follows, captions, and feed metadata.

Instead, original photos and thumbnails should be stored in **object storage**, such as Amazon S3 or Azure Blob Storage. The database stores metadata such as the photo ID, owner ID, caption, upload time, and object-storage key or URL. This separates large file storage from structured application data and allows photos to be delivered through a CDN.

## 6. What Each Component Solves

- **DNS:** Resolves SnapShare's domain name to the appropriate network endpoint.
- **CDN:** Serves frequently requested photos and thumbnails from nearby edge locations, reducing latency and load on the origin storage.
- **Load balancer:** Distributes incoming API requests across healthy application servers and avoids sending traffic to unhealthy servers.
- **Application servers:** Validate requests, authenticate users, manage uploads and feed logic, and coordinate access to storage and the database.
- **Cache:** Keeps frequently accessed feed data or metadata in memory to reduce repeated database queries and improve response times.
- **Primary database:** Stores structured and authoritative application data, including users, relationships, captions, and photo metadata.
- **Read replica:** Handles suitable read queries to reduce the workload on the primary database, with the possibility of brief replication lag.
- **Object storage:** Reliably stores original photo files and generated thumbnails without filling the relational database with large binary objects.
- **Message queue:** Holds thumbnail-generation jobs so image processing does not have to finish before the upload request can return a response.
- **Thumbnail worker:** Processes queued jobs, creates smaller versions of uploaded photos, and saves the thumbnails to object storage.

## 7. Step-by-Step Photo Upload Flow

1. A user selects a photo and submits an upload request through the SnapShare client.
2. The request reaches the load balancer, which forwards it to a healthy application server.
3. The application server authenticates the user, validates the file type and size, and checks upload limits.
4. The original photo is uploaded to object storage under a unique object key.
5. The application server saves the photo's metadata in the primary database, including its owner, caption, timestamp, and storage key.
6. The server places a thumbnail-generation job on the message queue and returns a successful response to the client once the upload and required metadata have been saved.
7. A background worker retrieves the job and generates a smaller thumbnail from the original photo.
8. The worker stores the thumbnail in object storage and updates the photo metadata or processing status if needed.
9. When users view feeds, the application retrieves feed metadata from the cache or an appropriate database, then provides photo URLs. The CDN serves the original photos or thumbnails from its edge cache, fetching them from object storage on a cache miss.
10. Cache entries are updated or invalidated when relevant feed metadata changes, so users do not continue seeing outdated information indefinitely.

The upload workflow should include failure handling: if thumbnail generation fails, the queued job can be retried, and the original photo remains available while the thumbnail is pending.

## 8. Trade-Offs

### Speed versus freshness

Caching feed metadata and using a CDN improves response times and reduces database and storage load. However, cached feed information may briefly be outdated after a user uploads a photo or follows someone. Cache invalidation, short time-to-live values, and refreshing important data help balance speed and freshness.

### Cost versus reliability

Using multiple application servers, a database replica, durable object storage, and background workers improves resilience and helps the system handle growth. However, these additional components increase infrastructure costs and operational complexity. SnapShare should add capacity based on measured traffic and reliability requirements rather than over-engineering from the beginning.

### Fast uploads versus immediate thumbnail availability

Processing thumbnails asynchronously allows the application to respond quickly without waiting for image resizing. However, a thumbnail may not be available immediately after upload, and queue delays or worker failures can increase processing time. The application should show a processing placeholder and retry failed jobs.

### Simplicity versus scalability

A single application server and database are easier to build and maintain at launch. As demand increases, adding load balancing, caching, read replicas, and workers improves scalability but introduces more components to monitor, configure, and debug. These components should be introduced when traffic or reliability needs justify them.

## 9. Conclusion

SnapShare should begin with a simple, well-organised application and scale based on measured demand. The estimates suggest approximately 579 average feed views per second, around 2,895 peak feed views per second, and 748.25 TB of new original-photo and thumbnail storage per year. Because the system is read-heavy and photo files consume substantial storage, the design prioritises CDN delivery, caching, read replicas, object storage, and asynchronous thumbnail generation. Monitoring latency, throughput, error rates, cache hit rate, storage growth, and queue depth will help guide future scaling decisions.
